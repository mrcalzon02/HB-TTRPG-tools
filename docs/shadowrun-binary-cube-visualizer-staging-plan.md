# Shadowrun Binary Cube Encoder Visualizer — Iterative Staging Plan

## Status

- **Repository:** `mrcalzon02/HB-TTRPG-tools`
- **Authoritative branch:** `main`
- **Current stage:** `V0 — Baseline Contract and Golden Evidence`
- **Implementation state:** Planning document established; no 3D visualizer implementation has been accepted yet.
- **Development rule:** Exactly one stage is active at a time. A stage must satisfy its exit gate before the next stage begins.

## Objective

Break the existing **Binary Cube Encryption Laboratory** into a companion **Binary Cube Encoder Visualizer** that remains a real, functioning encoder while making the internal transformation visible in a manipulatable three-dimensional environment.

The visualizer must show:

- a freely orbitable, zoomable, and pannable 3D cube environment;
- large, unmistakable input and output arrows;
- selectable cube faces;
- selected input and output orientation;
- the keyed three-dimensional point field;
- payload cells and deterministic filler cells;
- individual binary digits entering the selected input face;
- each binary digit being assigned to its canonical point identity;
- the fixed point field being read through the selected output projection;
- the final encrypted block leaving the selected encoding face;
- play, pause, step, reverse-step, restart, speed, and timeline controls;
- inspection of individual bits, points, face cells, block indexes, and transformation state;
- real package generation, validation, decryption, and round-trip verification through the canonical Binary Cube engine.

The visualizer is not permitted to become a decorative mock-up. Every displayed transformation must be derived from the same canonical operations that produce the actual encrypted package.

## Architectural Rules

### One computational authority

The Binary Cube engine remains the only authority for:

- key generation and validation;
- row, column, and depth permutations;
- mask placement;
- deterministic filler generation;
- face-coordinate mapping;
- quarter-turn orientation;
- point identity;
- input and output projection order;
- block transformation;
- encryption and decryption;
- package framing and checksums;
- omnidirectional collision-free validation.

The visualizer may display engine output, but it must never independently reproduce or approximate the encoding algorithm.

### No stacked engine replacements

The present runtime loads a base Binary Cube engine and then replaces it with large-grid and omnidirectional variants. Before the visualizer is allowed to depend on the engine, these behaviors must be consolidated into one canonical source-of-truth implementation or exposed through one stable canonical API.

The visualizer must not become another replacement layer, post-processor, mutator, or compatibility wrapper.

### One visualization pipeline

The visualization path must remain explicit:

```text
User Input
    -> Canonical Binary Cube Engine
    -> Canonical Transformation Trace
    -> Visualizer State Controller
    -> Single 3D Renderer
    -> Visible Animation and Inspection UI
```

The renderer does not calculate encryption. The controller does not alter keys or packages. The transformation trace is generated by the canonical engine and is treated as immutable evidence of what the engine actually did.

### Preserve existing workflows

The existing Encryption Laboratory must continue to support:

- manual binary input;
- file-to-bit conversion;
- key generation and import;
- package import and export;
- secure package export;
- decryption;
- diagnostics;
- custom key editing;
- authentication-related controls;
- desktop handoff or download controls;
- local browser persistence.

The visualizer is a companion tool and may later share controls with the laboratory, but its first implementation must not destabilize the existing laboratory.

### Truthful geometry

The current algorithm does not physically tumble bits through a solid block as though they were colliding particles. It assigns source-face cells to stable point identities in a keyed 3D point field, then reads those same point identities through another face projection.

The visualizer must represent that truthfully:

1. bits enter a two-dimensional input face;
2. input face order assigns each bit to a stable point ID;
3. bits travel from face cells to their keyed `(x, y, z)` point locations;
4. the point field remains fixed;
5. the selected output projection determines the read order;
6. bits travel from point locations to output face cells;
7. the output block exits the cube.

Camera rotation is a viewing operation. Input and output quarter-turns are encoding orientation operations. The interface must keep those concepts visually distinct.

## Performance Tiers

A grid size of `1024 × 1024` contains `1,048,576` point identities. It is not reasonable to create a separate DOM node or full mesh object for every point at all sizes.

The visualizer therefore requires explicit rendering tiers while the encoder continues to operate at full resolution:

- **Detailed animation:** Small demonstration grids, initially `3–12`, may animate every point and every bit.
- **Batched animation:** Medium grids may animate grouped rows, columns, tiles, or sampled point cohorts while preserving exact numerical state and selected-bit inspection.
- **Aggregate visualization:** Large grids may display density fields, instanced point clouds, selected slices, representative paths, and exact counters without pretending that every point is being individually rendered.
- **Encoding authority:** All tiers still encrypt and decrypt the complete full-resolution data through the canonical engine.

Any sampled or aggregated view must be clearly labeled as a rendering optimization, not an approximation in the encoder.

## V2 — Canonical Transformation Trace

### Goal

Teach the engine to describe what it did without changing what it did.

### Work

Add an immutable transformation trace generated by the canonical engine during one block transformation.

The trace must include:

- trace schema version;
- key ID;
- grid size;
- block index;
- source bit range;
- input face;
- output face;
- input quarter-turns;
- output quarter-turns;
- mask state;
- filler state;
- point field identity and coordinates;
- input face cell index for each point;
- source bit assigned to each point;
- output face cell index for each point;
- output bit order;
- final encrypted block;
- validation status.

Define explicit trace phases:

1. `source-ready`
2. `block-framed`
3. `mask-applied`
4. `input-face-staged`
5. `point-assignment`
6. `point-field-loaded`
7. `output-projection-selected`
8. `output-face-staged`
9. `encrypted-block-emitted`
10. `block-complete`

The trace must be produced from the same internal arrays used by encryption. It must not call a second independent implementation of the algorithm.

### Deliverables

- Trace schema.
- `traceTransformBlock` or equivalent canonical engine operation.
- Trace validator.
- Trace fixtures for all V0 vectors.
- Tests proving trace output reconstructs the exact encrypted block.

### Exit gate

V2 is complete only when the encrypted block generated from a trace is byte-for-byte identical to the canonical engine result and trace generation does not change package output.

# Required Implementation Boundaries

## Canonical engine additions

The visualizer may require new engine operations, but they must be implemented directly in the canonical engine rather than as a competing transformation layer. Likely additions include:

- `pointDepth(key, x, y)`
- `projectionOrder(key, face, quarterTurns)`
- `frameInputBlock(bits, key, blockIndex)`
- `traceTransformBlock(block, key, options)`
- `traceEncryptBinary(bits, key, options)`
- `validateTransformationTrace(trace, key)`

Names may change during V1 and V2, but responsibilities must remain explicit.

## Visualizer state

Visualizer-only state may include:

- camera position;
- camera target;
- selected point;
- selected bit;
- selected block;
- playback time;
- playback speed;
- render quality;
- visibility toggles;
- reduced-motion preference;
- active trace phase.

Visualizer state must not contain a second editable copy of canonical engine truth without an explicit validated handoff.

## Scene lifecycle

The renderer must have explicit operations for:

- initialize;
- load key geometry;
- load trace;
- set phase;
- set timeline position;
- select point;
- set rendering tier;
- resize;
- dispose trace resources;
- dispose key resources;
- dispose renderer.

Resource cleanup is part of correctness, not optional polish.

# Acceptance Definition

The Binary Cube Encoder Visualizer is complete only when all of the following are true:

1. It performs real encryption and decryption through one canonical engine.
2. It produces exactly the same package as the existing laboratory for identical input and key material.
3. Its animation is generated from an engine-produced immutable trace.
4. Every displayed bit can be tied to an exact source index, point ID, coordinate, input face cell, output face cell, and ciphertext index.
5. Input and output faces are directly selectable and engine-validated.
6. Large arrows make direction unmistakable.
7. The 3D scene is orbitable, zoomable, pannable, resettable, and inspectable.
8. Playback is deterministic under play, pause, scrub, restart, and reverse-step operations.
9. Large grids remain functionally encodable even when the rendering uses batching or aggregation.
10. The existing laboratory, custom editor, authentication, secure export, desktop handoff, and local persistence remain functional.
11. Reduced-motion and 2D fallback modes preserve understanding and control.
12. All stage exit gates have accepted evidence on `main`.
