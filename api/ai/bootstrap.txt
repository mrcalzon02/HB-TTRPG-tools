FOUNDRY AI BOOTSTRAP CONTRACT

For reasoning models, code interpreters, agents, and tool-capable hosts.

PRIME RULE

Mirrored calls, not mirrored logic.

Calzon's TTRPG Foundry contains authoritative generators, calculators, laboratories, resources, campaign-state systems, helpers, and personality definitions. Discover and use registered authority instead of recreating behavior from model knowledge.

Never claim execution, persistence, randomness, rendering, deployment, or tool access without observed host evidence. This file is a routing contract; referenced current machine authorities govern on conflict.

REQUIRED DISCOVERY

Start at /.well-known/ai-capabilities.json, then load only what the selected task requires:

1. /.well-known/ai-capabilities.json
2. /api/ai/status-vocabulary.json before interpreting status, acceptance, or execution-state vocabulary
3. /skills/index.json to select the minimum-capability skill that fits the task
4. /docs/blacklight/charles-personality-engram.json once for the orchestration context
5. /skills/{selected-skill}/SKILL.md
6. /api/foundry-capabilities.json only when the skill references capabilities
7. /api/operation-contracts.json only before constructing executable calls
8. /api/resource-collections.json only for registered static, campaign, or lore material required by the task
9. Check only the selected skill's executionRequirements and referenced helper requirements
10. Check host runtime and transport compatibility only for execution actually required
11. Run a declared deterministic self-test only before claiming self-test-passed or ready

Cache each loaded authority for the current orchestration context. Do not reload unchanged registries, contracts, helpers, resources, or persona. Follow exact selected-skill references instead of scanning sibling registries or unrelated collections.

Restricted browsers may use registered HTML compatibility projections for discovery; those projections never replace canonical JSON, SKILL.md, helpers, source code, or the Charles engram.

EXECUTION CLASSES

static-resource: retrieve the registered authoritative resource.

browser-js: load the declared canonical JavaScript runtime in dependency order and execute it in a compatible JavaScript host. Do not translate or recreate its algorithm. Use registered loaders and self-tests when available.

host-sandbox: use only registered helpers/scripts when the host satisfies declared requirements such as Python, Pillow, writable filesystem access, or cryptographic randomness. Repository presence is not execution.

browser-page-context: execute only inside the required initialized page context. If unavailable, report the limitation and registered authoritative interface; do not simulate hidden state.

browser-ui: behavior remains coupled to the declared UI. Do not invent headless APIs, JSON injection, DOM hooks, or alternate renderers unless registered.

live-sensor-browser-context: requires the declared browser, device, and sensor context. Never report simulated measurements as observations.

EXECUTION STATE

Static discovery and host execution are separate. A capability may progress through observed states such as runtime-required -> runtime-compatible -> self-test-passed -> ready. Never promote state without evidence. Static GET readiness does not imply discovered capability execution.

TRANSPORT

GitHub Pages is a static origin. Public files may be retrieved through GET when the host permits their content type. OpenAPI is discovery, not proof of executable RPC. Do not infer POST, RPC, MCP, browser control, or another execution service unless the machine manifest declares it and the current host verifies it.

ARGUMENTS AND DEPENDENCIES

For an executable operation, use /api/operation-contracts.json for exact operation IDs, call styles, argument order, names, types, ranges, units, enums, defaults, aliases, and returns. Do not invent public arguments. Preserve declared dependencies, tables, constants, modules, initialization, seed rules, random sources, and source ordering.

RANDOMNESS AND STATE

Use only randomness permitted by the selected skill. Never fabricate random results when its required trusted source is unavailable.

For persistent campaign/state operations, use the registered state-management skill and helper only with observed writable storage. Conversation state is transient fallback state. Never claim persistence without observed filesystem or host evidence.

CHARLES

Registered Foundry Agent Skills inherit blacklight.charles. Load the canonical engram once per orchestration context unless higher-priority host/system policy or an explicit out-of-character presentation request suppresses its presentation. Use charles-foundry-interface for Charles-facing or multi-skill requests. Charles grants no tools, permissions, credentials, network, filesystem, persistence, randomness, or execution state.

FAILURE

If authoritative capability execution is unavailable: identify the selected skill/capability, state the missing runtime/context/transport, identify the registered authoritative interface or resource, and do not manufacture an equivalent implementation.

RESULT PROVENANCE

When practical, report the selected Agent Skill, capability/resource ID, canonical source, operation, material arguments or seed, runtime, and observed execution/self-test state.

FINAL RULE

Discover authority. Load only required authority. Execute it when possible. Retrieve it when static. Use its declared interface when context-bound. Report inability when requirements are absent. Never substitute invented Foundry logic.
