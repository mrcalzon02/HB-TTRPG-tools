Iterative environment production kit

A portable record of the Beckenburg map and model production method, prepared 28 October 2026. It combines the workflow, measurable standards, actual failure investigations, a resumable map packet, an evidence validator and a GitHub Actions example. It is useful for another game or tabletop environment project after supplying that project's engine adapters and design constraints.

Iterative environment production

Use this workflow to advance an existing environment from its current verified stage. Preserve accepted work; do not regenerate a map merely because a new session starts. The portable package is an evidence and production protocol, not a replacement game engine or procedural map generator.

1. Read the project's instructions, latest handoff, current map packet and open defects. Inspect branch, HEAD and uncommitted work. Agree on one concrete milestone within the user's scope; audit existing terrain before adding structures.

2. Read the production guide for stage gates and standards and mathematics for geometry, support, lighting and capture contracts. Use project-specific tolerances and gameplay rules rather than importing Beckenburg constants blindly.

3. Build or refine the smallest useful batch. Follow dependency invalidation: terrain changes reopen support/routes; model bounds reopen collision and placement; lighting changes reopen material and blackout reviews. Record new defects immediately and identify older-map audit obligations.

4. Verify actual exported geometry, runtime integration and appropriate gameplay paths. Capture overhead and human-height views, plus close-ups of the changed details. Include negative and positive controls where a fix could hide the entire effect. Tests and attractive stills have separate scopes.

5. Read host adapters and evidence format to use scripts/production.py. Initialize a packet, attach real artifacts and reviews, and validate it. Never relabel native previews as runtime, offline rendering as measured FPS, or automated checks as human acceptance.

6. Publish source, exports, captures, report and a resumable handoff together when authorized. Verify remote commit and deployed artifact hashes separately. Preserve unresolved gates explicitly.

Read worked examples when diagnosing recurring errors or explaining why these standards exist. Provenance identifies the pinned source, original review reports and governing terms.

Host boundaries

- Reading these documents requires ordinary file or HTTP access. Python 3.10+ with a writable sandbox runs the evidence helper without third-party dependencies.

- Blender, renderer, physics, networking, audio and hardware tests remain project adapters. The helper checks the supplied evidence record; it cannot independently prove the recorded observation occurred.

- Static GitHub Pages provides discovery and downloads. It does not execute Python, edit a repository or render a game for a remote model. Use an authorized sandbox, CI runner or local host for those operations.

- In the Foundry inherit the registry's blacklight.charles presentation policy. No personality or skill grants tools, credentials or publication permission. The standalone production method does not depend on that persona.

The authored-environment production method

Purpose and scope

The method turns a location concept into a coherent, playable environment through repeated construction, observation and correction. Every pass has a purpose, a source of truth, an inspection scale and a recorded exit condition. The order matters because later detail depends on earlier geometry. It is expensive to dress a room whose staircase, foundations or service circulation still need moving.

This is a distillation of a developing project, not a claim that every Beckenburg map has completed every gate. Its strongest result is a repeatable way to expose and repair defects while preserving the distinction between planning, native authoring, real runtime output and human approval. Some maps are blockouts, others have substantial native detail, and individual runtime systems have targeted verification. Those states must remain visible.

1. Recover context before construction

Read repository instructions, the current milestone, the latest dated handoff, the defect ledger and relevant source/export manifests. Record checkout, branch, exact revision and dirty files. Preserve concurrent work. Find the actual active checkout rather than assuming a remembered folder is current. A duplicate rebuild can erase weeks of fit-out or quietly split geometry, collision and lighting between incompatible versions.

Choose a bounded milestone with a concrete result: for example, correct the creek culvert opening and its collision, or refine the boat while preserving its placement. Record the baseline, affected systems, proposed checks and captures. Keep broader completion goals separate from this batch. If a user requests a breadth pass, advance existing maps one named stage and retain each map's open risks; do not describe a shared template as many finished locations.

The handoff is executable context: exact artifacts, commands and outcomes; what is accepted, what merely passed a diagnostic; unresolved defects; next unfinished action. Conversation history is supporting context, not the only copy of production knowledge.

2. Location identity and measured planning

Give each map an authored lore name and a stable machine ID. The mission selector should display the lore name; shorthand such as house or school remains an internal family. A placeholder selection image must be labeled as such until replaced by an actual roadside or van-perspective capture.

Define normal use, occupants, period, geography, access, services, architectural identity and the interruption that made the site interesting. Consult references appropriate to the place. Record the source URL, drawing or photograph identity, what was inspected and what remains uncertain. Draw an original measured plan; numbering in a generated image is not reliable geometry.

Create a map-specific asset needs list: standard furnishings, installed fixtures, utilities, unique working machinery, vegetation, clutter, narrative objects and interactive pieces. Each item needs a physical purpose, approximate dimensions, support, placement constraints and reuse/authoring decision. A sawmill needs a logway and a saw arranged to cut the moving log. A small workshop bandsaw does not acquire that purpose merely by being placed beside a log carriage.

Rough blockouts reserve relationships and route capacity. They are cheap design instruments. Do not treat colored area rectangles, a navigation graph or room names as a built environment. Preserve them as a baseline while real terrain and architecture replace their provisional affordances.

3. Terrain first, including interior-heavy locations

Establish units, axes, origin, height range, drainage, water level, boundaries, buildable pads and access from the canonical vehicle. Mark the playable area and off-site scenery separately. Author slopes and embedded paths rather than floating route ribbons over a flat plane. Walked paths often cut into their surroundings; beaches need sand, gravel or rock transitions rather than grass continuing into water.

Apply the desquareify gate after rough blocking. Remove zone-shaped pads and rectangular material stamps from the actual terrain. Shape the playable footprint into meaningful lobes, constrictions, coves and approaches. A loose rectangle with wobbly corners is still a rectangle. Straight edges need a physical reason such as a building, retaining wall or engineered road.

Use hedges, stone walls, banks, fences, fallen timber and landform to frame the site, while explicit player blockers protect water and dangerous edges. Visual boundaries and physics boundaries must agree. A berm should read as earth with varied cross-sections, believable slopes and material continuity. Repeated gravel blobs stuck to a dirt-colored vertical wall do not make a natural bank.

Unify the site and distance: foreground ground, banks, near vegetation, distant trees, haze and sky should share a controlled palette and scale. Billboard foliage can fill distant canopy gaps while existing dimensional trees remain. Near foliage needs believable density without turning every shrub into a hiding location. Far scenery should extend the world beyond the berm without implying reachable terrain.

Inspect an overhead silhouette, oblique aerial views, arrival at the actual van, standing and crouched paths, and cross-sections through steep or wet areas. Check grades, supported feet, capsule movement, foundation contact and water barriers. A nice overhead view can hide a sheer bank or an impassable route. Terrain acceptance requires both physical and visual evidence.

4. Architecture and service systems

Build against accepted terrain. Geometry, room ownership, collision, apertures, stairs, fixtures, acoustic zones, spawns and vehicle connection must derive from shared authored coordinates. Keep feet elevation distinct from eye elevation. A level can have a good plan and still fail vertically.

Walls, floors and roofs need physical thickness and correctly oriented visible undersides. Separate adjacent finishes rather than layering full coplanar faces. Openings must actually cut the surfaces they cross. Stairs need a continuous supporting surface, treads, head clearance, lower-ceiling clearance, an exact upper deck void and guards that leave the route open. Inspect from above, below and both landings. Graph connectivity cannot establish that a player fits through the stairwell.

Doors need correct hinge origin, mounted elevation, frame relationship, swing sweep, open/closed collision and shadow state. Do not normalize their pivots like floor-standing props. Inspect an elevated storey and multiple door states; a leaf that looks acceptable closed may vanish or detach when opened.

Plan power before decorative lamps. Place physically supported fittings, switches, cables or distribution where needed, and an operable breaker. A remote site still needs a generator and distribution plan if ghost activity can trip the electrical system. Source-running and breaker state are separate. Battery, oil and fire sources retain their own supply semantics. The vehicle has its own interior supply; a site blackout should not accidentally erase the player's working base.

Reserve routes, cupboard interiors, evidence access, ritual areas and spawn clearances before large furniture. Use actual swept movement from the vehicle to required destinations. Verify operating poses and aim rays for controls in darkness as well as light. Networked state must use the host's authoritative door, power, object and encounter data.

5. Supplementary models as environment engineering

Search the real source library first. For a candidate, inspect its native bounds, pivot, axis convention, material slots, normals, UVs and texture images. Record source identity and hash. Keep originals intact and make explicit derivatives. A library model's semantic purpose and visible quality form the minimum benchmark for new models around it.

Author a missing model for its job. Start with scale, silhouette and functional parts, then joint continuity, curves, thickness, supports and assembly. Organic statues need a coherent sculptural surface, not visibly disconnected primitive limbs. A boat needs an actual inner hull curve; seats and oars must fit it. A culvert needs an exposed opening through terrain, not a tube buried behind an uncut bank.

Inspect the model in isolation and in its installed setting. Check underside, back, close silhouette, normals, UV orientation, repeated textures, contact shadows and interaction distances. Keep native pivots for hinges and fixtures. Uniform scale may be appropriate; stretching unrelated furniture into machinery is not.

Only then refine surfaces: purposeful material families, local wear, dirt accumulation, joints, edges, paint variation and believable aging. Preserve clean and worn variants where reuse matters. If a wear-only pass is intended, compare vertices, normals, indices, UVs and transforms to prove geometry stayed unchanged. Do not repaint a source texture to hide an importer flip or a lighting error.

Export source assets and runtime derivatives with a manifest. Reopen the delivered files and compare their transforms, bounds, object IDs, packed textures and geometry against the authoritative export. A successful exporter invocation is insufficient if the saved scene omitted fixtures or packed the wrong images.

6. Placement, density and repeated refinement

Place major furniture and facilities for understandable use: seating around a hearth, storage near work, toilets and bins where a path destination needs a reason, a landmark at a terminating trail. A campground needs enough camps and support equipment to read as a campground. Repeating two tents or aligning every tent north–south makes the site feel provisional.

Add meaningful groups of small objects supported by the actual desk, shelf, mattress or ground part. Test rotated footprints, overhang and clearance, not only origin height. A bed's headboard maximum is not its sleeping surface. Recheck supported children when a parent table moves. Keep door approaches, sight lines, ritual zones and movement routes open.

Refine in loops: place a useful batch, capture it, inspect errors at the appropriate scale, fix and repeat affected checks. More clutter is not automatically more quality. Sparse sites may need vegetation and rocks, but a failed model silhouette or crude texture needs repair before another pile of props. Track quantities and purpose by zone so dressing has a reason and remaining model work is visible.

Hiding locations are gameplay resources. Decorative shrubs must not silently become hide sockets. In Beckenburg each investigation site shares the same maximum allowance, including indoor and outdoor candidates, and the highest difficulty can yield zero. Other games should encode their own rule explicitly and test it globally rather than accidentally varying difficulty by foliage density.

7. Runtime lighting, camera and material review

Use the actual renderer after export. Native authoring previews answer different questions. Capture arrival, entry, each floor, facilities, stairs both ways, outbuildings, water edges and changed models. Include a broad aerial view, human-height route views and close defect views. An aerial flyover should frame real site anchors and hand off to the correct player/vehicle pose without assuming every site has indoor room rectangles.

Review mains on, mains off, torch-only and independent light supplies. Test both sides of boundaries, below lofts, above ceilings, at corners and at grazing angles. A straight camera can conceal leakage. For a repair include a negative control that should be dark and a positive control that must stay lit; otherwise disabling light everywhere could appear to fix the problem. Check openings remain useful instead of plugging doors or stairs to achieve darkness.

Hold camera, time, exposure, render preset and non-target state constant for before/after images. Record which binary and assets produced each frame. If changing only a material, verify unaffected geometry and lighting stayed stable. A low-resolution art style still requires coherent texel density, UVs, palette, silhouette and material reading; arbitrary stripes and coarse primitive assemblies are not style requirements.

For animation record deterministic simulation times and multiple viewpoints. Check actual playback advances, not just that a poster exists or a file has metadata. Offline six-second output is not proof of twelve real-time frames per second. Physical performance needs a separate measured run on the claimed hardware.

8. Story detail, loose physics and optional encounters

After function and broad visual quality, tell the site's story through small supported traces: work interrupted, ownership, repairs, accumulated use and deliberate absences. Avoid evenly distributed random litter. Identify which items are fixed scenery, examinable objects or real pickups. A mesh does not become a loose physics object by naming it one; it needs mass, collision, ownership, authoritative state and persistence/reset rules appropriate to the game.

Author optional location-specific encounters separately. For example, looking into the dock water with a light could trigger an original mask-and-bubbles scene. Define observation cone, duration, distance, cooldown, reveal/hold/retreat phases, abort conditions, reset and witness synchronization. Do not present this design packet as an implemented feature. Keep optional scares distinct from ordinary evidence and scoring unless the design explicitly connects them. Use owned or properly licensed audio and models.

Recheck paths, supports, hiding allowance, photographs, interactions and authority after final scatter. Tiny props can obstruct a drawer or cover an evidence face. The story pass is the last construction phase, not an exemption from physical fitness.

9. Defect ledger and regression propagation

Every discovered issue receives an ID, affected maps/assets/systems, reproduction conditions, evidence, impact, cause if known, fix revision, status and regression obligation. Include wall/floor/roof/corner light bleed, unsupported items, interpenetration, bad UVs, detached doors, inaccessible controls and regressions introduced by fixes. Preserve history; a failed check is valuable production knowledge.

Distinguish discovered, reproduced, fixed in source, targeted checks passed, awaiting visual review and accepted. A shared helper repair does not mean all older maps were audited. Record a per-map matrix for old content. When requirements improve, use that matrix to upgrade older sites rather than silently raising their status.

Invalidate downstream evidence when inputs change. Terrain edits reopen foundations and routes; changed model bounds reopen colliders and supported clutter; lighting changes reopen blackout/material/evidence checks; a new camera path reopens flyover bounds and final pose; story scatter reopens routes and interactions. Re-run checks affected by the delta, then broaden only for real uncertainty or shared-system impact.

10. Close a milestone without losing its limits

Deliver sources, runtime exports, tests, labeled captures and a dated handoff together. Build the shared gallery from the real artifacts. Check local generated files, then remote commit containment, then deployed page and image hashes. These are three distinct delivery checks.

Record acceptance by scope: native geometry, runtime image, gameplay route, multiplayer authority, hardware performance, human visual approval. A map is only complete when its declared required gates pass and the appropriate reviewers accept them. Budget exhaustion, a successful build, a large asset count or an attractive presentation does not close those gates.

The next developer should be able to recover the exact baseline, understand what changed, rerun the checks and continue from one named unfinished action. That continuity is how repeated small passes accumulate into a coherent production rather than a sequence of disconnected demonstrations.

Standards, contracts and mathematics

These are engineering review contracts, not statutory construction standards. Numeric tolerances, capsule size, art budget and quality targets belong in each project's packet. Beckenburg examples explain decisions; they are not universal constants.

Shared coordinates and physical identity

Use a declared unit and handedness. For Beckenburg-style metre, Y-up, yaw-only placement:

x_world = tx + cos(yaw) * x_local - sin(yaw) * z_local
y_world = ty + y_local
z_world = tz + sin(yaw) * x_local + cos(yaw) * z_local

Apply uniform scale before this transform. Apply it once to mesh, collider, support anchors, lamps and interactions. Rotate an offset collision centre too: an origin at the back of a sofa is not its collision centre. For arbitrary transforms use the full world matrix; transform normals with the inverse transpose of its linear part and renormalize. Record negative/nonuniform scale deliberately, including winding implications.

Keep standingSurfaceY, eye offset and asset mounting plane separate. Source mounting origins can be at the top of a ceiling lamp or the hinge of a leaf. Floor-centering normalization is appropriate only when the source contract allows it. Source hashes, units, axes, pivot, bounds, material slots and export transform are required asset metadata.

Support and placement

At a placement (x,z), query the actual supporting triangle/part and its height, not the maximum Y of an entire furniture bounding box. For a support plane with normal n and point p0, solve n·(p-p0)=0 for Y where |ny| is sufficiently nonzero. A nearly vertical plane is not a tabletop.

Transform every relevant footprint vertex into world space. Test containment in the usable support polygon, account for intended overhang, and compare the object's bottom/contact points with the support surface within a recorded tolerance. Corners-only tests can miss concave gaps; use polygon intersection or triangulated support sampling as appropriate. Check clearances against actual neighboring parts, not just the parent's outer AABB.

For terrain, grade is abs(deltaY) / horizontalDistance; reject zero horizontal spans or handle them explicitly. Evaluate both ends, interiors, bends and cross-slope. Centreline samples alone do not prove a player-width path is supported. Validate a swept capsule/shape with the project's step, slope and clearance limits. Native triangle support, movement collision and rendered feet must agree.

Walls, floors, stairs and doors

Author thickness, normals and openings as physical data. Give floors a downward-facing underside and closed edge where needed. Avoid duplicate coplanar finishes; frame, trim and decals need an intentional surface relationship. Beckenburg's historical 80 mm offset on each partition side is its construction convention, not a recommendation for every building.

For a stair ramp from horizontal endpoints a to b, calculate t = dot(p-a,b-a)/dot(b-a,b-a) in XZ, clamp only for the intended segment, and interpolate surface Y between endpoints. Test width, treads, headroom and both landing transitions. Cut the upper deck and lower ceiling using exact opening bounds, including fractional coordinates. Derive guards and their collision from the same aperture and leave the approach open.

Represent doors by hinge, leaf extent, elevation, frame and angular state. Compute swept collision and rendered vertices from the same data. Door state changes must invalidate relevant visibility and light caches. Test closed, intermediate and open poses, including upstairs doors. A pass at floor zero says nothing about elevated leaves.

Light and power

Separate fixture geometry, emitter orientation/color/range and electrical state. Use explicit source/breaker/circuit dependencies; do not attach independent vehicle, battery or fire sources to site mains accidentally. Test reachable control poses with useful visibility in blackout conditions.

Occlusion queries must protect the receiving surface before applying prop self-shadow bias. A large bias can move a receiver through a thin wall. Cache identity must include every input that changes visibility: source, receiver context, geometry revision, relevant door/window state and any normal/endpoint assumptions. Invalidation is part of correctness, not merely performance.

Use quantitative checks only with a declared region, threshold and expected outcome. For leakage, compare light-on behind a closed boundary with source-off, and retain a same-side lit control. Include open-aperture controls so a blanket blocking repair fails. Probe corners, floor/roof joins and grazing camera angles. Native triangle scenes may need their own visibility adapter; do not invent room walls around outdoor meshes to satisfy an indoor helper.

Materials and low-resolution visual quality

Check source UVs, image orientation, resolution, repeat mode, atlas boundaries, interpolation and normals before repainting. Preserve comparable texel density. Periodic wear must tile in both axes without a forced directional stripe dominating the object. Dirt should respond to use and material rather than uniformly darkening everything.

A material-only change should preserve geometry/UV/material identities and unaffected tiles where possible. Compare hashes of unchanged data, then inspect actual in-room frames under matched conditions. A metric such as stripe contrast proves one property, not overall art quality. Model silhouette, density, surface response and palette still need visual review against the project's approved reference quality.

Water, transparency and projected evidence

Water should be a reusable surface module with defined shape, placement, wave parameters, flow direction/speed, transparency/depth absorption, edge behavior and editor handles. Multiple surfaces need compatible phase and boundary rules, not merely adjacent rectangles. Boat dry volumes should follow the inner hull and survive the full wave cycle, with a control showing surrounding water remains present.

For depth-driven effects use camera-forward distance: d = dot(worldPoint-cameraPosition, cameraForward). Match water and opaque depth to the same completed camera frame and simulation time. Euclidean distance and raw hardware depth are not interchangeable. Render opaque geometry before dependent transparent layers; define sorting/compositing semantics explicitly.

A useful attenuation model is T = exp(-absorption * pathLength) with opacity 1-T, optionally bounded by an authored range. This describes transmission, not necessarily physically accurate scattering. Foam from visible opaque depth/normals should discriminate shore contacts from submerged flat beds and lifted props. Screen-depth contacts cannot prove offscreen collision. Spray particles need declared lifetime, motion, depth tests and budget.

Projected dots should mark the first relevant beam intersections on the ghost surface, replacing hits that would otherwise land on room objects. Covering the whole ghost collider with arbitrary dots is a different effect. UV evidence needs a supported outward face offset or thin volume so it avoids surface burial/z-fighting; expose it through the actual UV light semantics. A planned effect remains unverified until its production renderer, photo/evidence rules and authority behavior are tested.

Capture protocol and comparison

Record map ID, revision, runtime binary hash, asset manifest, camera position/orientation/FOV, resolution, preset, simulation time, lights, weather, door state and control scenario. Use immutable binaries during a capture session; rebuilding a JAR in use can break lazy loading even after screenshots were written.

Capture completion requires successful process exit and expected artifacts. Inspect the image, not only file size. For video also verify duration/frame count, actual decoded motion and browser playback time progression. Keep exact baseline and candidate camera matrices stable when comparing a repair. Include overview, standing/crouched route, changed detail, underside and adverse-angle views where relevant.

Classify evidence explicitly: planning; native geometry; runtime render; gameplay; multiplayer; hardware performance; human review; publication. No class implies the next. An offline 72-frame sequence sampled at 12 simulation frames/second establishes six simulated seconds, not achieved hardware FPS.

For performance report hardware, driver, build/preset/resolution, warm/cold state, sample duration and frame-time distribution (p50/p95/p99). Separate CPU/GPU/readback stalls where measured. Compare identical workloads; do not compare a software CI renderer with a real Windows GPU and call the difference an optimization.

Approval and evidence freshness

A passed test validates its stated property and inputs. Artifact hashes identify bytes, not truth. Review records need a reviewer, outcome, date, input revision and explicit scope. Human acceptance must be recorded by an actual human; an agent's inspection remains an agent review.

Evidence becomes stale when its dependencies change. The portable packet uses one exact input_revision for every passed gate; any revision change conservatively requires renewed gate records. Larger pipelines can replace this with a dependency DAG and per-input hashes, but must not preserve old green results without proving unchanged dependencies.

Keep critical unresolved defects open. Scope a partial milestone honestly instead of declaring a whole map complete. Production acceptance is a policy decision based on the recorded evidence and the project's quality benchmark; the supplied validator only enforces record integrity and declared gate requirements.

Worked investigations: why the gates exist

The examples below are recorded project observations, not new tests executed by this portable package. Their source reports are pinned in source-index.json at Beckenburg revision db6c5b6a93d00426d8cc7b2c0f69515b824e0e75. Review pages provide the actual images; source reports preserve hashes and limitations. No example establishes final acceptance of every map.

A lighting helper passed while the real game leaked light

The 28 October investigation found that a tested architectural visibility helper was not called by production FixtureLighting. A prop self-shadow endpoint bias could also move the receiver across a thin wall. Ordinary face-on views hid the problem; a grazing camera revealed it.

The repair connected the receiving-side check before bias and scoped cache entries by receiver context. A controlled synthetic light on actual Blackpine geometry produced sample energy 4.8 before the repair and 0.187 afterward, equal to ambient. The grazing diagnostic counted 2,260 bright leak pixels before and zero after. Same-side illumination remained as a positive control. Geometry was held constant, so this was not a wall thickening disguised as a lighting fix.

Production-path regressions covered 6,789 closed wall/floor/corner probes across nine indoor maps, plus 1,784 clear stair rays that had to remain clear. Eighteen actual OpenGL diagnostic images and successful before/after process exits were recorded. The result is targeted lighting evidence. Native mesh joins, every portal state, animated route pans, installed performance and human acceptance remained open.

Method gained: test the real sampler, use receiving-side bias logic, include adverse views and positive controls, and preserve the distinction between broad probes and whole-map art acceptance.

Runtime diagnostic review

Metal looked bandaged because the texture contained a stripe generator

The 27 October material investigation traced black/gray banding to the procedural IRON tile: every eighth X pixel was darkened by 17 levels. UV repetition stamped those grooves across broad surfaces. Adding geometry or changing exposure would have hidden the symptom without addressing its source.

The tile changed to bounded two-dimensional wear, fine grain and sparse pits. The other fifteen atlas tiles remained byte-identical, as did renderer, fixture-lighting and vehicle-layout classes in the comparison binaries. Groove phase contrast fell from about 16.652 to 0.0569. Twelve actual OpenGL van frames used six matched cameras, vehicle supply on, site breaker and torch off. Exact runtime atlas/tile exports accompanied the result.

That proves this tile's targeted repair under those conditions. Roof/interpolation behavior and native GLB metal families were still separate work. It does not mean every metal material in the game was approved.

Method gained: inspect procedural texture code, compare actual runtime pixels, hold unrelated systems constant, and measure the suspected defect without promoting that metric to total visual quality.

Matched metal review

A broad camera audit exposed indoor assumptions on an outdoor map

The 26 October compatibility pass recorded 64 scripted actual OpenGL samples across ten investigation sites and Castle, covering camera/light conditions. An outdoor flyover had assumed room bounds and failed on Hollow Creek. Framing changed to finite site-owned anchors, excluding the long approach and van from the main site frame where appropriate. A software fallback no longer invented rectangular buildings to represent outdoor space.

Six prototype long halls also had single fittings outside useful entry range. Repeated physical fittings addressed their entrances while refined House/Farmhouse/School layouts were preserved. Broad camera and entry-power tests were useful, but the report explicitly excluded whole-map, LAN, human and real-time performance acceptance. Twenty-eight planning packets remained planning rather than becoming runtime maps because a gallery existed.

Method gained: test every current map family when changing shared camera or lighting code; preserve map maturity states; use real site identity rather than room-count assumptions.

All-map compatibility review

Boat, water and the danger of repairing the wrong layer

Hollow Creek review exposed water inside the rowboat, seats crossing the hull, oars intersecting its sides, and broken-looking texture/lighting. These needed separate diagnoses. Hull-shaped dry sections addressed water exclusion; seats and oars needed measured model fit; the GPU texture path had an extra V flip and downsampling that damaged atlas appearance. Repainting the boat would not have repaired the importer.

The water work developed into an independent module with shape/placement and parameter controls, geometric wave motion, depth absorption, shoreline contact foam and spray. Review cameras were moved to beach, banks and dock because an aerial view could not show these effects adequately. Texture travel, geometric displacement and contact effects were reviewed independently.

Recorded sequences used deterministic simulation time and multiple views. Browser playback was checked because an earlier video delivery showed a still poster but did not play. The water report and original module retain their own implementation and licence records; the portable workflow does not bundle that engine or claim its shader can execute on static Pages.

Method gained: separate source mesh, importer, lighting, transparency and capture failures; inspect contact geometry; verify animation and playback rather than assuming a video container proves motion.

Water runtime review

The standards became stricter through specific observations

Several decisive requirements began as visual catches: a sawmill cutter that served the wrong scale of work; light under a loft; square terrain surviving beneath decorative boundaries; crude statues and uniform tent orientation; distant greens mismatching near grass; a culvert blocked by uncut terrain; decorative foliage accidentally implying extra hiding capacity.

The response was to make each observation a reproducible check and an older-map audit obligation. Terrain became a prerequisite to structure refinement. Desquareification had to affect physical terrain and materials. Model fitness included purpose, scale, support, joint continuity and installed appearance. Remote sites required power distribution compatible with ordinary ghost breaker behavior. Hiding budgets became explicit across indoor and outdoor candidates. Final storytelling became a distinct stage after functional fit-out.

These are improvements to the production process, not evidence that all historical content already meets the improved standard. The ledger and per-map acceptance matrix are what make that difference actionable.

Running the method locally, remotely and in CI

The portable boundary

The package contains one canonical Python evidence helper. Its HTML guide is a reading projection, not another implementation. Local agents, web agents with a Python sandbox and CI all invoke the same helper. Project adapters provide actual scene generation, rendering, movement, audio, multiplayer and hardware tests. No Beckenburg engine, Blender installation, purchased asset pack or private workstation path is required to read or validate a packet.

Use python scripts/production.py init <new-directory> --map-id <stable-id> to create a fresh packet and handoff. The command refuses an existing destination. All gates start open. Complete them in the order documented in WORKFLOW.md; preservation of existing work may mean auditing an already built stage rather than reconstructing it.

Packet v1 contract

packet.json is UTF-8 JSON. Paths are relative to its directory. No absolute paths, .., backslashes, symlinks escaping the packet root or network URLs are accepted as local evidence paths. Remote sources belong in provenance documentation, not in the local hash slot.

| Field | Contract |
|---|---|
| `schema_version` | integer `1` |
| `map_id`, `lore_name` | nonempty strings |
| `input_revision` | exact 40-character lowercase Git SHA for the inputs being reviewed |
| `gates` | every gate from `manifest.json`, exactly once |
| `artifacts` | unique IDs; relative path, SHA-256, evidence kind, input revision |
| `defects` | unique IDs, summary, severity, status, affected scope, reproduction, regression |
| `handoff` | relative path to a real nonempty handoff file |

A gate has id, status (open, blocked, passed), evidence artifact IDs and review. A passed gate needs a nonempty reviewer, valid ISO date, scope, outcome pass, current input revision and at least the gate's required evidence kinds. Its manifest depends_on prerequisites must also be passed; for example architecture cannot pass before terrain. The human gate also requires reviewer_type: human; automated/agent review cannot substitute for it. This is an attestation field, not authentication: policy must identify who can write that record.

Artifacts have id, path, sha256, kind, input_revision. Evidence kinds are enumerated in manifest.json. A passed gate cannot cite an artifact from another input revision. The helper verifies bytes, reference integrity and required evidence types, but cannot decide whether a screenshot depicts the claimed engine or whether an attestation is truthful. Review the artifacts and the capture logs.

Defect severity is critical, major or minor; status is open, fixed or accepted. A fixed defect needs fix_revision equal to the current input revision and evidence IDs; an accepted defect needs a documented acceptance reason. Complete mode rejects every unresolved defect, including minor ones: explicitly accept a known limitation if project policy allows it. Accepted limitations must remain visible to the final reviewer.

Validation exits 0 for a structurally valid, honest in-progress packet. Open gates are printed as open, never green. --require-complete rejects any open/blocked gate or open defect. Malformed records, stale passed gates, missing files and hash mismatches fail in either mode. JSON and HTML reports make these states reviewable.

Attach real results

1. Record the exact input commit and copy/export artifacts into the packet directory. Do not hash a mutable file while a renderer is still writing it.

2. Record successful process completion separately in the capture/test report. Include source/build hash, camera/state, command, tool versions and limitations.

3. Run python scripts/production.py hash <artifact-file> and insert that SHA-256 into the artifact record. The command hashes one file; it does not approve it.

4. Reference the artifact IDs from relevant gates. Add review records only after the corresponding inspection actually occurred.

5. Run validate and generate report. If any input changes, update the input revision and reopen or renew affected evidence. This v1 helper intentionally treats revision freshness conservatively.

Gate kinds represent minimum record coverage. For instance, a runtime image and a gameplay report are not interchangeable. Multiple screenshots of one corner do not cover every required room; the gate review scope must describe coverage and missing areas. A project should add more specific checks in its engine adapter instead of weakening the packet's meaning.

Engine adapter examples

- Blender/source: generate or import geometry in declared units; export native bounds, world matrices, UV/normal counts and packed image hashes; reopen the saved source; capture overhead, underside and model inspection views.

- Runtime renderer: load the actual export, use fixed cameras/state and immutable binaries, save frame metadata and images, exit cleanly. Add animation sequences where motion matters. Do not publish native viewport images under this adapter's label.

- Physics/gameplay: sweep the actual player shape from canonical arrival through required spaces and controls; test door states, stairs, water barriers and supports. A graph-only path is insufficient.

- Power/lighting: on/off and independent-source cases; real production sampler; negative and positive controls; doorway/stair openness; cache invalidation; representative old-map regression matrix.

- Network: host/client state agreement for doors, power, object ownership and encounters, including reset and late join where supported.

- Hardware: measured installed gameplay and frame times on named hardware. A headless GPU capture can support a rendering claim but not this claim automatically.

The pinned source index links Beckenburg's implementation/tests/build tools so a developer can examine the concrete adapters. Commands and classes are source references, not a promise that they execute inside the Foundry repository. Adapt them to the current engine and installed toolchain.

GitHub Actions

examples/validate-environment.yml is a manually dispatched example. Copy it to the target project's .github/workflows/, adjust the skill path and packet path, and run with ordinary read-only repository permissions. It validates a checked-in packet, requires complete gates and uploads the review report. It does not execute shell code from JSON, install game dependencies or claim to render anything.

For a real rendering pipeline, add explicit, reviewed commands before validation to build the target engine and collect evidence. Prefer pinned toolchain/action revisions according to the target repository's policy. Untrusted pull-request code must not receive publication secrets. Uploading artifacts is not Pages deployment or human approval.

The Foundry's own validate-environment-production.yml runs helper regression tests and checks that the packaged HTML/ZIP are current. Its success validates this tool package, not any map.

Web and remote-model use

Start at the public skill HTML or SKILL.md; retrieve only relevant references. If the host can read text but cannot execute Python, use the guide to review/design and hand the packet to an authorized execution host. State that limitation. If a sandbox is available, download the ZIP, verify its sidecar hash and unpack it into a dedicated working directory before running tests.

Static Pages offers public reading/downloads only. Repository commits, workflow dispatch, engine execution and gallery publication require separate authorized transports. The skill must not imply that loading a manifest grants them.

Preservation and publication

Use a scoped commit containing only this batch. Fetch/reconcile before push and never force away concurrent work. Preserve local artifacts if connectivity fails. Record publication as pending until the remote contains the commit; record website delivery separately after deployed bytes match expected hashes. Retry transient failures modestly through an already authorized transport.

For migration include the packet, source/export manifests, defect ledger, reproducible commands, actual logs, capture metadata and latest handoff. Keep exact local paths out of portable instructions. Preserve third-party licences and original source identities; a workflow archive is not permission to redistribute paid models.
